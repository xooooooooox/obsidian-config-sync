# store ↔ remote 补齐:四档方向规则,item 与 key 两级 — design

Date: 2026-08-20 · 迭代 **2.25.0**(带 `schemaVersion` 4 → 5,故不走 2.24.4)·
Scope: 段 C(`store/` ↔ remote store)的能力补齐 **+ Sync Center 两段关系共用一个面板** · Status: 待评审 ·
Mock: 视觉伴侣本地会话 `round1-scope` / `round2-direction` / `round3-copy-and-crypto` / `round4-sidebar` / `round5-unified-panel` / `round6-open-questions` / `round7-remote-passphrase`(全部已定稿)·

owner 三处裁定:**不分阶段**,item 级与 key 级一轮做完;**面板统一**,remote 不再是一块单独的屏(见 5);**每个 remote 一份密码短语**(3.9 的方案丙),同轮做掉。

## 1. 现状:三段链路,能力不对称

| 段 | 动作 | 规则载体 | 粒度 |
|---|---|---|---|
| **A** `.obsidian` ↔ `store/` | Capture / Apply | 每项的 `fields` / `fileRule` / `perElement`,各自两层(共享 + 本机) | 键级、整文件级、名单元素级 |
| **B** `store/` ↔ 同 vault 其它设备 | 不由本插件承担(store 是 vault 内容,随笔记整体搬运) | 无 | 无条件 |
| **C** `store/` ↔ remote store | Pull / Push | `Remote.excludeSelf` | 仅 self 一项 |

段 C 今天的具体形态:

- **单位是 store 里的文件**,且**从不解析文件内容**,只问「两侧字节相等吗」(switch list 按集合比是唯一例外)。
- **Pull** 读两侧全部文件建两张映射表,分成「远端独有 → 写入」「本地独有 → 保留」「两侧都有且不等 → 冲突」,冲突交给用户一次性二选一,写入单位是整份内容。这个选择**不被记住**,同一份数据下次再问一次(issue 原话「每次 Pull 都要手动按 local」)。
- **Push** 遍历本地全部文件原样发出,内容相同则跳过,远端多出来的文件镜像删除。**连决策点都没有**。
- **面板**只读:一份 diff 列表加两个整份按钮。

**一个已有、但被压扁的能力。** `status.ts` 的 `itemFreshness` 已经逐项判方向(newer / older / equal / undatable),`perItemRemoteState` 却把整个 remote 压成一个 `RemoteState`,并在「两边在不同项上互相领先」时返回 `null` —— 注释原话是这种情况「`RemoteState` 没有词形容」。**逐行方向不是要新造的能力,是把已有的判断呈现出来**;做完之后那个 `null` 分支描述的情形自然有了词:一行一个方向。

## 2. 决定

### 2.1 四档方向规则

| 档 | 图标 | 含义 |
|---|---|---|
| `Both ways` | `cloud` | 推也推、拉也拉。默认。 |
| `Push only` | `cloud-upload` | 我的照样覆盖他;他改了什么都进不来。 |
| `Pull only` | `cloud-download` | 接他的;我的不出去,他那边保持原样。 |
| `Neither way` | `cloud-off` | 两个方向都不走。 |

四个词是同一套语法(都在回答「往哪个方向流」),对仗闭合:`Both ways` ↔ `Neither way`,`Push only` ↔ `Pull only`。控件是**点一下换一档的循环图标**,与「谁共享这个值」那个控件同一种手感;循环顺序即上表顺序,末档回首档。

否掉的方案:两个独立开关(push / pull 各一个勾)。理由是卡片里每一行的控件共用一条右对齐的轨,双开关的宽度会把那条轨撑歪;而且逐键区一行一个控件,双开关会让 Keys 区变成一片勾选框。

### 2.2 两级作用范围

同一个控件、同一套词,作用范围不同:

| 级别 | 落点 | 适用 |
|---|---|---|
| **整项** | 这一项与这个 remote 的关系 | 所有项 |
| **每个键** | 这个键与这个 remote 的关系 | 逐键模式的项(含字段级加密的项);明文 JSON 的整文件项 |

**键级是整项的子集,不是「更严」。** 四档不是一条链而是一个格:`Push only` 与 `Pull only` 互不可比。正确的约束是**方向集合的子集**:

| 整项 | 键的循环里有哪几档 |
|---|---|
| `Both ways` {推,拉} | 四档全开 |
| `Push only` {推} | `Push only` · `Neither way` |
| `Pull only` {拉} | `Pull only` · `Neither way` |
| `Neither way` {} | 无 —— **Keys 区整个隐藏** |

**UI 上缩短循环,不画置灰。** 这是「点一下换一档」的控件,没有下拉列表可以安放灰项与解释;解释放在 Keys 标签下一行小字 `limited by This remote`,而整项那一档就在 Keys 区正上方。

**存储不改写,运行时求交集。** 先设了 `Pull only` 的键、整项后来改成 `Push only`,该键存值不动,实际生效取交集(此例为空),照实显示 `pull only — nothing flows`,图标画实际生效的那一档。整项改回 `Both ways` 时该键自动复活。不静默改写用户写下的值,与仓库既有做法一致。

### 2.3 加密按形态两分,分水岭是**存储形态**,不是能否解密

**判定依据是这一项在 store 里长什么样,与此刻解不解得开无关**:

| 存储形态 | 此刻能否解密 | Keys 区 | 比较 |
|---|---|---|---|
| 明文 | — | 有 | 正常 |
| 字段级加密 | 能 | 有 | 正常 |
| 字段级加密 | **不能** | **有**(键名是明文) | 无法比对 |
| 整份加密 | 能 | **没有** | 正常 |
| 整份加密 | 不能 | 没有 | 无法比对 |

- **字段级加密**(逐键模式,其中某些键标了加密):store 里那份仍是正常 JSON,**键名是明文**,只有那些键的值是密文串。**两边同密码时**,扣留一个键搬的就是那串密文,传输全程不需要看懂它;**两边异密码时**(3.9 的转码路径),该键必须以目的地的密码存在,所以要过一遍明文。逐键两种情况下都提供。
- **整份加密**(整项加密,或整文件规则标了加密):**只给整项四档,没有 Keys 区。**

**整份加密不给逐键的理由只有一条,要写准。** 曾经的理由「传输不解密,不想为它开这个口子」在采纳 3.9 之后**不再成立** —— 转码路径本来就在解密再加密。留下的是 UI 那条:**列出键名需要当场解密,于是 Keys 区会随解锁状态出没**;解锁时写下的键级规则在锁上之后照样生效,却看不见也改不了。

由此得到一条通则,两处判定依据不同不是不一致,而是它的两面:

> **只读的判断可以随解锁状态变,可写的控件不可以。**
>
> 比较结果降级成「无法比对」没有代价;一个控件今天在明天不在,代价是用户写下的规则变成隐形。

两种形态在行上用两个不同字形区分:`key-round` = 字段级,`lock` = 整份。今天面板只有一个加密标记,这是新增的区分。

### 2.4 规则挂在 `Remote` 上,不挂在 item 上

remote 的名字是**这台设备的传输接线**,只在本地有意义。写进 item 的规则会随该项的 store 副本推到对面 vault,在那里指向一个不存在的 remote。

具体挂在**每个 remote 对象内部**,而不是新开一个顶层字段:`remotes` 整个字段已经是「只属于这台设备、永不进 store」的锁定规则,嵌在它内部的东西自动继承这个待遇;放顶层就要再补一条同样的保护规则。

## 3. 数据语义

### 3.1 Pull

以**本地 store 副本**为底稿,远端的值盖上来,被扣留的键不盖。段 A 的 apply 侧已有这个函数(`mergePreservingSanitized`:incoming 全面胜出,只有匹配模式的键保住底稿的值,包括只有底稿有的键)。

`Neither way` / `Push only` 的整项:该项的全部文件从 pull 的两张映射表里剔除,与今天 `excludeSelf` 的做法完全一致。

### 3.2 Push:必须保留对面的值

以**远端那份**为底稿,我的值盖上去,被扣留的键不盖。同一个函数,只是换了谁当底稿。

**这一条不能省。** store 里存的是整份文档,不是补丁。若把被扣留的键直接删掉再推,远端 store 里那份就真的没有这个键了,对面下次 apply 会把他活配置里的这个键一并删掉 —— 我们并不想动他的值,结果把他的值删了。

远端也没有该键时,整个省略。

先例:capture 遇到本机例外的键就是这么做的,注释原话「leave the store's existing value exactly as it found it」。

push 本来就已经读远端那份文件(用于「内容相同则跳过」),不是新增的 IO。

`Neither way` / `Pull only` 的整项:该项的全部文件从 push 的发送集合中剔除,并**同时从镜像删除的循环中豁免**(与 `excludeSelf` 今天的做法一致 —— 对面自己的那份不是我们该删的)。

### 3.3 「一致」的重新定义

**「一致」从此表示「在允许流动的方向上没有待办」,不再表示「两边字节相同」。**

两处都需要它:

- **方向性规则**:一个 `Push only` 的项,对面自己改了内容。两边字节不同,但那是不该进来的方向,我这边也没有要推的新东西 —— 这不是待办,归进「一致」那一组折起来,无勾选框。
- **逐键规则**:带扣留键的项两侧**按设计**就不同。若不改,这一项会永远挂在「有差异」里,推一次还在,拉一次还在。

判定方式:两侧各自把受规则约束的键蒙上,再比剩下的;蒙掉之后相等即为一致。

已知代价:对面确实变了而这一行不告诉你。否掉的候选是「多露一行说明对面改了什么」,理由是那一行会长期挂着而用户什么都做不了,久了就是噪音。

### 3.4 store lock 的三条

1. **lock 绝不学 remote。** lock 文件自己就是被推送的文件之一,任何与 remote 有关的字段都会被推到对面,在那里指向一个不存在的 remote。这是禁令,不是省事。
2. **pull 后的记账要区分两类项。** 今天对远端 lock 条目是原样照搬,理由写在注释里:「这些条目描述的就是我逐字节拷贝过来的内容」。带扣留键的项不再成立(拿到的是「他那份,但某些键还是我的」),这类项必须按合并后的实际内容重新盖章。代码里已有同形状的分支(用户选了保留本地的冲突项走的就是重新盖章)。
3. **指纹快路对带扣留键的项失效。** `itemFreshness` 今天「两侧都有指纹且内容记录相等就直接判等」。这类项的指纹按设计永不相等,必须退回 3.3 的蒙键比较。需要把「这一项对这个 remote 有没有键级规则」作为输入传进去。
4. **推送时送出去的 lock 要按实际推送内容重算,不能原样发本地那份。** lock 文件本身是被推送的文件之一。带扣留键的项,我们发出去的内容不是本地那份,若把本地 lock 原样发过去,对面就拿到一本指纹与自己文件对不上的账本 —— 而它正是对面设备判断「我和我的 remote 谁更新」的依据。做法:push 生成一份**派生 lock**,凡内容被改写过的项按实际发出的内容重算指纹,其余原样;本地 lock 一个字节不动。这是计算不同的值,不是新的格式,所以 lock 的 schema 仍然不变。
   **同一条规则暴露出一个既有缺陷,本轮一并修掉**:今天一个设了 `excludeSelf` 的 remote,push 会跳过 self 的内容文件、也豁免它的镜像删除,**却仍然把本地 lock 原样推过去**,于是对面 lock 里的 self 条目被我们的覆盖,描述的是一份我们根本没发的文件。派生 lock 的规则天然覆盖它:凡不参与推送的项(`Neither way` / `Pull only`),派生 lock 保留对面原有的条目。

加密项的比较另见 3.8。

### 3.5 方向感知的忽略集

今天 `checkRemote` / `remoteLockAhead` 各收一个 `ignoreRefs` 集合。四档之后一个集合不够:

- 「远端是不是有东西值得拉」这个问题,要忽略所有不参与拉的项(`Neither way` + `Push only`)。
- 「我这边有没有东西该推」这个问题,要忽略所有不参与推的项(`Neither way` + `Pull only`)。

落地为两个集合,或一个按方向查询的函数,实现时定。**不能沿用一个集合** —— 否则一个 `Push only` 的项会因为对面更新而永久点亮一个任何 Pull 都清不掉的箭头,这正是今天 `ignoreRefs` 注释里点名要避免的那个 bug。

### 3.6 派生 lock 的构造规则

**没有新格式**:派生 lock 就是一份 `store.lock.json`,字段一个不多一个不少,只是值按下表算出来。

| 字段 | 规则 |
|---|---|
| 参与推送的项的条目 | 取我们的;内容被改写过的项(带扣留键),指纹按**实际发出去的内容**重算 |
| 不参与推送的项的条目(`Neither way` / `Pull only`) | **保留对面原有的条目**;对面没有就不写 |
| 顶层 `capturedAt` | 派生值:合并后条目集里最新的捕获时间(schema 本就写明它是派生的) |
| `syncedWatermark` | **保留对面原有的值**。它的定义是「这个 store 跟到了它所拉取的 remote 的哪一步,只有 pull 会推动它」,我们的推送不是他们的 pull。**这是对今天行为的修正** —— 今天整份覆盖会把我们的 watermark 盖到对面头上 |
| `version` | 我们这个构建写出的格式版本。对面是旧格式时,先按现有的重新键入逻辑解析其条目,再按我们的格式写出 |

### 3.7 推送期间 remote 发生变更

**git 类型:已有的乐观并发控制是安全的,保持不动。** 推送全程是「克隆到临时目录 → 改文件 → 提交 → `git push origin <branch>`」,普通推送,不带 force、不带重试。克隆之后对面若有新提交,这次推送因非快进被拒,抛错走错误卡,**什么都没写进去**。而且读与写都发生在同一份克隆里,所以 3.2 那个「先读对面的值再写回」的动作要么整批落在克隆的父提交上、要么整批被拒,没有中间态。

**vault 类型:今天无保护(最后写入者胜),B 之后必须补。** 这一段从「覆盖」升级成「读-改-写」,出现真实的时间窗:读到对面的值,写回时对面刚捕获过,于是把旧值复活。规则:**写前复核** —— 每个被改写过的文件落盘前再读一次,与计划时读到的不一致就**中止整次推送**并如实报告。不是重试:推送不是幂等操作。

**第三层,与并发有关但更常撞上:面板上的 diff 可能来自最多 5 分钟前的缓存克隆,而推送用的是一份全新克隆。** 用户勾选的是**哪些项**,不是哪些字节;字节在推送那一刻重新读。重读后若某个勾中的项方向已变(本该推,现在对面更新),**中止并请用户重看**,不照过期判断推送。

### 3.8 加密内容:解密后比明文,不比密文

**事实澄清。** 每份密文自带随机盐和随机数,同一段明文加密两次字节就不同 —— 即使密码相同。同一个 vault 里字节稳定,是因为两台设备共用同一份 store,且捕获时明文未变会原样复用已有密文。**跨 vault 不成立**:两边各自独立捕获过,明文相同、密码相同,密文也不同。

**今天的状态。** 记账本对**任何需要密码的项**(整份加密的,以及只要有一个字段加密的项)根本不写指纹,注释原话是「一个永远对不上的指纹比没有指纹更糟」。所以项级新旧判断已退回按捕获时间比。但**文件级 diff 仍在比字节**,于是这类项在 remote 面板上永远显示有差异 —— 3.3 要消灭的那个常亮态,今天就已经存在于加密项上。

**决定:比较解密后的明文,各自用各自的密钥。** 本地那份用本地密码解,对面那份用**这个 remote 的密码**解(3.9;未配则沿用本地密码,即两边同密码的既有情形)。信封里本就带着**明文的 HMAC**,存在的理由正是「每次加密 IV 都不同也要能确定地比较」,所以比对是确定性的,不必逐字节较真密文。密钥派生很贵(PBKDF2 21 万次),但按「密码 + 盐」记忆化,而存量信封的盐是固定的,同一个信封每次会话只付一次;相对于每次比较都要克隆一个 git 仓库,可以忽略。

于是这类项有**三态,不是两态**:

| 状态 | 条件 | 面板表现 |
|---|---|---|
| 一致 / 有差异 | 两侧都解得开 | 与普通项完全一样 |
| **无法比对** | 本机未解锁;或这个 remote 的密码没配、配错 | 照实说明,不下差异结论,方向退回按捕获时间判 |

**「无法比对」的三种说法要分开**(mock round7):没配 —— `work-vault's copy is encrypted with a different passphrase.` + 通往 Settings 的入口;配错 —— `The passphrase saved for work-vault doesn't open its copy.` + 同样的入口;**对面还没有这一项的副本 —— 什么都不说**,行照常是一条待推的普通行。密码对不对只有真的试过才知道,没试过就下结论是在陈述一个我们并不知道的事实。

**「不写进账本」与「比较时解密」不矛盾**,这是本轮一处曾经混淆的地方:账本会被推到对面、进 git 历史,写明文指纹等于给小值的字典攻击开门;而比较发生在本机内存里、密码就在手上。一个是持久化的取舍,一个是当场的判断,不是同一个问题。

### 3.9 remote 的密码短语:采纳「每个 remote 一份」(方案丙)

今天整个 vault 只有一个密码短语,存在这台设备本地(不在 `data.json` 里,不随同步走),用来加解密**自己 store** 里的加密项。一个 remote 是另一个 vault 的 store,它的密文可能是用另一个密码加的,后果比「看不看得懂」更重:比较解不开;**拉取把对面的密文搬进本地 store 后,apply 用本地密码去解 —— 解不开,应用直接失败**;推送反过来同理。

**决定:每个 remote 一个可选的密码短语。** 存法照 Access token 那套 —— `data.json` 里只存一个钥匙串条目名,**密码值本身进系统钥匙串,绝不落 `data.json`**;同款保留名守卫,不得选中本地密码那个保留条目。所有 remote 均为桌面专属,无手机侧问题。

**默认值是这条设计的关键:留空 = 与本地同一个密码。** 今天「两个 vault 共用一个密码」的情形走的还是原路(密文原样搬运,一个字节不动),丙是**纯增量**,不改变任何现有行为;只有显式配了一个不同的密码,转码那条路才被激活。

四个使用点:比较(3.8,各自用各自的密钥)、拉取(用对面的密码解、用本地的重新加密)、推送(反过来)、以及加密字段的键级扣留 —— 异密码时「只搬密文串」的便利没有了,每个加密字段都要过一遍明文。

#### 3.9.1 信封复用:不做就是 bug,不是优化

每次加密都会生成一个全新的随机盐,所以重新加密**必然**产生新字节。不做处理的话,每次推送都会重写每一个加密项,git 历史每次被搅一遍,面板上那一行也永远到不了 `In sync`。

规则:落盘前先问「对面那份信封是不是已经装着这段明文」(信封自带的明文 HMAC 就是为这种确定性比较存在的),是就整个跳过不写。于是真正会重新加密的只有两种情况:

1. **内容真的变了。**
2. **一次性转换** —— 这一项第一次开始跟这个 remote 走,把本地密码封的那份换成对面密码封的那份。每项只发生一次。

**被扣留的键不参与重新加密**:我们保留的是对面已有的那个值,它本来就是用对面的密码封好的,原封放回即可。

#### 3.9.2 失败模式:宁可不动,也不写脏

密码没配、或者配错:

- **比较**:报「无法比对」(3.8 的三种说法)。
- **拉取**:**跳过那一项并说明,绝不把一份用不了的密文写进本地 store。** 运行照常完成,能拉的都拉;报告里那一项单列一行 `Skipped — the passphrase saved for <remote> doesn't open its copy. Nothing was written.` 今天的照搬密文在同密码时是对的,异密码时就是往自己的 store 里塞一份永远解不开的东西,而且要到下次 apply 才炸,离现场很远。
- **推送**:同理跳过并说明。

#### 3.9.3 密钥派生的容量压力

派生按「密码 + 盐」记忆化,缓存上限 256 条且**满了整个清空**。转码之后两侧的盐会一起挤这一个缓存,加密项多的 store 有被反复清空的风险。读侧的盐是固定的(付一次、之后命中),**写侧每次重新加密都是全新的盐、跨运行无法缓存** —— 这正是 3.9.1 必须做的原因:它把这笔钱限制在真正变了的字段上。实现时留意缓存容量是否需要上调。

## 4. 持久化形状

### 4.1 `data.json`:新增字段 + 一次 schemaVersion 迁移

形状按仓库既有习惯(分类由结构承载:先分区、再分 id,两层嵌套,与 `items` 及 store lock 的 `items` 一致,不把区和 id 拼成扁 key):

```
remotes[i].items:
  <section>:
    <id>:
      direction: "both" | "push" | "pull" | "none"      // 整项,缺省 = both
      keys:
        <pattern>:
          direction: "push" | "pull" | "none"           // 每个键,缺省不写
```

`keys` 的映射键就是键名模式(支持 `*`),与每项自己那套逐键规则同构:模式即映射键,不再重复一个 `pattern` 属性,保证只有一个真源。缺省值一律不写盘。

**`excludeSelf` 折叠掉。** 它表达的就是「`community/config-sync` 这一项 `direction: "none"`」。两个字段说同一条规则,正是「一个概念一个词」禁止的事。折叠会让旧版本读新文档时漏掉这条规则,所以走 **`schemaVersion` 4 → 5**,加一次迁移把旧值翻译过去,之后不再写 `excludeSelf`。

**`remotes[i]` 另加一个可选字段:`passphraseId`**(3.9)。与 `tokenId` 同型:钥匙串条目名,`^[a-z0-9-]+$`,不得等于本地密码那个保留名;**密码值本身绝不进 `data.json`**。缺省 = 与本地同一个密码。

新增 definitions:`remoteItemRule` / `remoteKeyRule`。**先改 `schema/data.schema.json`,再动代码。**

### 4.2 `store.lock.json`:不改,且明令不许知道 remote 的存在

见 3.4 第一条。行为改动见 3.4 第二、三条,格式一个字不动。

### 4.3 `store/` 目录:不改

store 里是被捕获的内容;规则属于本地接线,扣留发生在传输那一刻,不落盘。没有新文件、新命名、新层级。

唯一要注意而不需要改结构的一点:**一条键规则作用在哪个文件上是运行时才知道的**。一个只给某个设备类用的键,它的 store 值在那份分设备类的附属文件里,不在主文件里。所以扣留逻辑要同时覆盖主文件与附属文件,3.3 的蒙键比较同理(lock 的指纹本来就是按「主文件加附属文件」划的)。

### 4.4 localStorage:不改

面板的勾选状态**不跨会话记忆**,与段 A 一致(每次重开按各行方向默认)。

## 5. UI:一个面板,两段关系

**本轮最大的结构决定,owner 提出并裁定:remote 不再是一块单独的屏。** 今天主面板与 remote 面板是两套渲染器;本轮统一成一套,remote 专用那套退役。

理由是**它们本来就同构**。三处按状态分桶的区域 —— 侧边栏的分区计数徽章、主面板的筛选药丸行、顶部的状态药丸组 —— 结构一模一样,不同的只是那套状态词。而 remote 专用渲染器一直在还债:它自己实现了一份没有折叠、没有勾选框、没有 chip 的「静态版」分区头,DESIGN 里记着「要与主列表的头/体结构对齐需要改 DOM,故意推迟」。

顺序上的理由同样硬:**不先统一,四档控件、chip、命运句就要一个个焊进一个即将删掉的壳里,全是白干。**

### 5.1 两套状态词一一对应

| 这台设备 ↔ store | store ↔ remote |
|---|---|
| To capture | To push |
| To apply | To pull |
| In sync | In sync |
| Not synced here | Doesn't sync with this remote |
| No settings yet | Nothing captured yet |

前五个桶严格对应,三处区域直接换词。各自多出一个对方没有的桶,**不得硬塞进对方的词表**:

- 设备侧独有:可用性轴(没装 / 被禁用 / 仅桌面)。store 副本存不存在与本机装没装无关,所以这根轴在 remote 关系下**整个撤掉**。
- remote 侧独有:**Can't compare**(加密项且本机未解锁,见 3.8)。

**设备关系下这三块一个像素都不变。** 统一是让同一套组件在另一段关系下换一套词,不是改动现有界面。

### 5.2 关系选择器(采纳候选乙)

侧边栏今天把两个问题混在一列:上半截「筛哪一类项」,下半截「看哪一段关系」,而选中下半截会改变上半截的含义。

采纳的形态:**分区列表头部新增一个 `View` 选择器**,remote 收进它的下拉;侧边栏此后纯粹回答「筛哪一类项」。下拉每一项自带徽章(`This device ↔ store` ↑11 ↓1 / `store ↔ main` ⇣4 ⇡2 / …),所以「哪个 remote 需要处理」不必先切过去就能看见。

紧凑切换器(窄面板 / 手机)是侧栏的下拉替身,同样带上这个选择器,不另立一套。

### 5.3 行

- 与设备关系同一套行解剖:折叠箭头、名字、留白、chip 群、命运句、勾选框。
- **chip 一律只有图标,说明在悬停提示里**。四档 chip 只在非默认档时出现;整项与键级各出一个,可并列。加密两分用两个字形:`key-round` 字段级 / `lock` 整份。
- 命运句:`Pushes settings` / `Pulls settings` / `Doesn't sync with this remote`(`Neither way`,灰行、无勾选框,与设备关系下「本机不同步」同一长相)/ `Nothing to send`(3.3 的一致态)。
- 折叠行:`N items match this remote` / `N items don't sync with this remote`。
- 底部按钮按方向各跑各的勾选行:`Pull N` / `Push N`。勾选框的含义两段一致:**这次运行带不带这一行**。

### 5.4 卡

标准行序,不适用则省略:

- `On pull` / `On push` / `State`
- `Files`
- `This remote` —— 整项四档循环控件
- `Keys` —— 逐键各一档,受 2.2 的子集约束(循环缩短,Keys 标签下挂 `limited by This remote`)

**没有 Keys 区的四种情形,分两类处理:**

前三种是**结构事实**,用户改不了,不解释就成了没来由的空缺 —— 照实说明,不留空:

| 情形 | 文案 |
|---|---|
| 整份加密的项 | `This file is stored as one encrypted blob — it travels whole or not at all.` |
| 非 JSON 的整文件项(css / js / txt) | `No keys in this file — it travels whole or not at all.` |
| 文件夹项 | `A folder travels as a whole — the direction above covers every file in it.` |

第四种是**用户刚做的选择**:整项 `Neither way`。**Keys 那一行完全不渲染**,不留分隔线、不留高度 —— 正上方就写着 `Neither way`,再说一遍是复述,而既有规矩正是「不建值的行完全不渲染」。

**`Push only` 且远端更新时,卡里照常显示对面变了什么。** 3.3 否掉的是「在**列表行上**长期挂一行说明」;卡片要点开才看得见,用户点开就是想知道细节。规则:**列表保持安静,卡片有问必答**。`Files` 的徽章在这里**没有方向**(既有徽章是「方向图标 + 数量」,而这些文件不会流动),改用中性的 `files` 字形,悬停说明这些变化留在对面;文件条目照旧 `+ ~ −` 三色。`State` 行:`<remote> changed N files. Push only, so they stay there.` 这同时补上了 3.3 记下的那条已知代价。

**卡片只显示当前关系的那条规则**,另一条给入口:设备关系下是「谁共享这个值」,remote 关系下是「往哪个方向流」。两条都摆进去,卡片会变成设置转储。

**`On push` 那句是全案最要紧的文案:必须明说被扣下的键保留对面现有的值**,否则用户会以为那个键被删了。定稿措辞:

> `Overwrites this remote's <Item>. <key> keeps whatever <remote> already has.`

### 5.5 状态栏

状态栏在视图之外,没有「当前关系」可言,所以**同时报两段**:设备 ↔ store 的待捕获 / 待应用项数,加上**所有 remote 汇总**的待推 / 待拉项数,悬停补一句跨几个 remote。

单位由此统一为**项**,顺带修掉今天那处不一致(`↑↓` 数项,`⇡⇣` 数 remote —— 同一行里两种单位)。

### 5.6 Config Sync 自己那一项收进面板

今天设置里那个「Config Sync 自己的设置不参与这个 remote」开关,加面板底部复述它的一行小字,一并撤掉。它就是这一项的 `direction`,改完之后是面板上一条普通的行,迁移时按原设置填入。

**同一个对象两副面孔,要写清楚何时是哪种**:设备关系下它是钉在顶部、没有勾选框的特殊行(「自己管自己」);remote 关系下它是一条普通的、可设四档的行。

### 5.7 Settings 的 remote 编辑器

**加一行**:`Passphrase`,与 `Access token` 完全同一个控件(Obsidian 自己的密钥选择器:链接或新建、掩码显示、✕ 解除链接),下面挂同款条件状态行(`✓ Passphrase stored on this device.` / `⚠ 这台设备还没有这个条目 —— 在这里链接一次`),留空时不画状态行。同款保留名守卫:不得选中本地密码那个保留条目,照 token 今天的做法弹一句「换一个」。

标签就叫 `Passphrase`,与 General 里那个同名 —— 它在 remote 编辑器里,归属不会误解。说明进悬停:`Only if this remote's vault uses a different passphrase than yours. Leave empty when they match.`

**撤掉一块**:「Keep Config Sync's own settings out of this remote」那个开关连同它的说明整块移除(5.6)。

### 5.8 统一带来的三条新规矩

1. **只有对面才有的项。** remote 那边可能有本地清单里根本没有的项,而设备关系下每一行都来自本地清单。统一后的行模型必须容忍「没有本地对应物的行」(remote 面板今天已会降级处理,本轮把它写成通用规则)。
2. **搜索与筛选药丸在 remote 关系下照常可用**(今天选中 remote 会禁用搜索)。
3. **remote 专用渲染器独有的三样东西要找到新家**:行内的文件级 diff、插件开关的逐个翻转清单、「有 N 个文件只有你这边有」那段说明。前两样落进卡片既有行序(`Files` / 卡内清单),第三样并入 3.3 的一致性叙述。

## 6. 不在本轮

- **冲突选择的记忆化。** 现象:拉取逐个文件比两边,两边都有而内容不同的文件是**冲突**,弹窗逐个问「保留我的 / 用他的」;选完只作用于这次运行,**什么都不记**,下次同样的分歧再问一遍(issue 原话「每次 Pull 都要手动按 local」)。记忆化就是在弹窗上加一个「以后这一项都这样」的勾。
  **不做的理由:四档已经把它说完,而且说得更准** —— 「永远保留我的」= `Push only`,「永远用他的」= `Pull only`,键级同理。再做一套记忆表就是**两个机制说同一件事**,正是折叠 `excludeSelf` 时避免的那种重复。真正剩下的只有手感:规则要去卡片里设,而那个勾让人在正想着这件事的当口就写下规则。**将来要做,做法是「这个勾直接写入四档规则」,不另起一张记忆表。** 顺序上也应在后:冲突弹窗本身在本轮会变(逐行选择、被扣留的键如何在冲突里表现),先改完再加捷径。
- **勾选状态跨会话记忆**(见 4.4)。

设计层面的开放问题**已全部收拢**(mock round6 定掉键级子集的画法、四种没有 Keys 区的情形、`Push only` 展开卡;round7 定掉 remote 密码短语的表单与三种失败态)。剩下的是实现期需要盯的两件事,不影响开工:

## 8. 验收(真机)

1. 一个整项设成 `Neither way`:面板灰行、两个方向都不动、`N items don't sync with this remote` 计数正确、该项不再影响 remote 的方向箭头。
2. 一个整项设成 `Push only`:推得过去;对面改了之后拉不进来,且该行显示 `Nothing to send` 而不是常亮的待办。
3. 一个键设成 `Neither way`,拉:对面的其它键进来,该键本地值纹丝不动。
4. 同上,推:**去对面 vault 核对该键的值原封未动**(这是 3.2 的验收点,必须真机比对,不能只看本地报告)。
5. 反复拉推同一项:不出现「推完还有差异、拉完还有差异」的常亮态(3.3)。
6. 字段级加密的项:Keys 区正常列出键名;**已解锁**时该项能判出一致/有差异(不再恒显差异),**未解锁**时报「无法比对」而不是弹密码框。
7. 整份加密的项:没有 Keys 区,照实说明;比较行为同上一条。
8. 从 2.24.3 升级:原 `excludeSelf` 为 true 的 remote,迁移后 Config Sync 那一行是 `Neither way`;设置里的旧开关与面板底部小字均已消失。
9. 推送之后去对面核对 `store.lock.json`:带扣留键的项,其指纹与对面自己的文件对得上;不参与推送的项(含 Config Sync 自己),条目仍是对面原来那条,没有被我们覆盖。
10. **面板统一**:切到 remote 关系后,搜索、筛选药丸、分区计数徽章、分区全选、卡片展开全部可用,且三块计数区域用的是 remote 那套词;切回设备关系,界面与 2.24.3 逐像素一致。
11. **两轴独立**:选中 `Community plugins` 分区,再切换关系,分区筛选保持不变(不被重置)。
12. **状态栏**同时报两段,单位都是项;悬停说明覆盖了几个 remote。
13. **窄面板与手机**:紧凑切换器带关系选择器,双徽章在 360px 下不挤掉名字。
14. **一次性转换**:给一个 remote 配上不同的密码短语,推送一个加密项 —— 去对面 vault 用**它自己的**密码打开,内容正确。
15. **稳态安静**:内容不变时连推两次,第二次不重写任何加密项(git 无新提交),面板上那一行是 `In sync` 而不是常亮待推。
16. **密码配错**:拉取时那一项被跳过并说明,**本地 store 未被写脏**(该项文件字节不变),其余项照常拉进来。
17. **扣留的加密键**:推送后去对面核对该键的值原封未动(与第 4 条同法,但这一项是加密的)。
18. **对面还没有这一项的副本**时:行上**没有**任何密码相关的提示,是一条普通的待推行。
